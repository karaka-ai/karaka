# Agent Note: 标准托管拉取请求运行器

Status: implemented

[English](2026-09-02-standard-hosted-pull-request-runners.md) | 中文

## 问题

自动拉取请求检查使用组织自有的 16 核运行器标签。这些标签需要仓库外部的运行器配置和付费大规格运行器容量，因此公共仓库无法只靠仓库配置执行必需的源码检查。标签不可用时，作业会一直排队而无法分配机器。

工作流还按照 16 核机器设置门禁、覆盖率、lint 与快照并发。若直接选择较小的标准运行器而不减少这些进程数，就会让宿主过载，并把调度压力变成不可靠的测试证据。

## 决策

自动拉取请求作业使用 GitHub 标准托管容量：Linux 作业与 Cloudflare 预览构建使用 `ubuntu-latest`，原生 Windows 作业使用 `windows-2025`。3 个 Linux 工作作业与 4 个原生 Windows 作业仍相互独立，因此每个作业只获得一台运行器，并保留现有的诊断职责。`ci-master.yml` 中的大规格运行器手动基准测试仍只能通过 dispatch 触发。

自动 Linux 与 Windows 作业会在对应控制项存在时，把顶层门禁调度、lint 工具、发布检查、浏览器 worker 与快照进程限制为 2。覆盖率会让 2 个相互隔离的单 worker 插桩分区与 1 个豁免重型 worker 并行运行，同时活跃的顶层覆盖率门禁不超过 2 个。此配置优先保证标准容量上的可靠完成，而不是大规格池的延迟目标。

并发门禁共享同一个 checkout。因此，源码语料扫描在 glob 发现之后遇到 `ENOENT` 时，会将其视为临时文件所有者已经完成清理；其他读取失败仍然是致命错误。

`DSH_CI_FAILOVER_LINUX` 与 `DSH_CI_FAILOVER_WINDOWS` 开关为可信的同仓库分支保留自托管回退。选择器要求拉取请求的 head 仓库与目标仓库相同，并继续排除 Dependabot。因此，即使设置了故障切换变量，fork 拉取请求也仍在临时标准运行器上执行。

## 曾考虑的替代方案

**继续把大规格运行器作为自动默认值。** 不予采用，因为每个拉取请求都会依赖付费的组织容量和本仓库无法自行配置的运行器标签。

**把自托管运行器作为自动默认值。** 不予采用，因为持久机器会增加外部可用性依赖，并且绝不能执行 fork 提供的工作流代码。

**合并独立作业以分配更少的机器。** 不予采用，因为公共仓库的标准计算不需要大规格运行器计费，而合并会串行化互不相关的证据，并让故障更难分类。

## 后果

自动拉取请求计算不再依赖 GitHub 托管的大规格运行器。独立作业仍会各自分配标准机器，并且可能因每台机器容量较小而耗时更长；任何作业都不会同时分配标准运行器与自托管运行器。Actions 产物和缓存存储、手动派发的大规格运行器基准测试以及 Cloudflare 部署仍是分别管理的资源。

聚焦的工作流测试会拒绝自动大规格运行器标签，固定降低后的 worker 预算，并要求每个自托管选择器都包含同仓库保护条件。完整平台矩阵仍负责证明较慢的标准运行器能否满足现有作业截止时间。
