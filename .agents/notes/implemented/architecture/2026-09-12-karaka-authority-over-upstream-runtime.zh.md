# Agent Note: 在保持上游运行时不变的前提下提供 Karaka 权限归属

Status: implemented

[English](2026-09-12-karaka-authority-over-upstream-runtime.md) | 中文

## Problem

Karaka 的持久聊天和应用工具需要应用、租户和用户隔离。把这些字段放入 DSH Session 头会要求修改严格的格式编解码器及其消费者。复制所有依赖包会扩大上游维护范围，却不能证明这些实现需要不同的行为。

## Decision

Karaka 应用配置复用 DSH 的 Session、Agent、循环、Tools、JSONL、查询和模型实现。独立身份服务使用原有 JSON 存储和 domain API，在 Session 文件之外保存持久权限归属。内核锁保证每个归属存储根目录只有一个写入者。创建过程先预留身份，在等待完成的 setup 中绑定实际尚未发布的 Session，并在归属数据和 Session 都持久化后确认成功。冷访问在引擎恢复前完成授权。子会话沿经过验证的持久父会话链解析归属。

Karaka HTTP 操作通过公开 API 调用原始引擎。Profile 使用上游 DSH 启动器；其就绪通知触发独立的 [Karaka 启动守卫](../../../../packages/karaka/transport-http/src/startup.ts)。守卫仅在所有已启用的 Loader 条目均处于活动状态时接收后端或浏览器请求。导入、激活、依赖等待或禁用表达式异常使入口保持关闭，并请求以退出码 1 执行有时限的进程关闭。实际禁用的条目仍是可选的。Webserver 注入通过 DSH 已有的必需条目策略，使守卫自身的失败成为致命启动错误。独立维护的 SDK 使用这些路由，不再嵌入另一套 Session 实现。

Karaka MCP 包拥有应用工具目录。连接监督和丰富结果转换通过[程序化扩展](2026-09-14-shared-mcp-extensions-for-karaka.zh.md)使用共享 DSH 实现；该决策取代本记录中复制 MCP 的部分。[来源清单](../../../../packages/karaka/mcp-application/UPSTREAM.json)记录共享代码与自有适配器。没有复制依赖实现。应用工具在符合条件的各个 Agent 作用域注册，不在全局注册；工具必须同时获得端点许可和预设的明确允许，继承作用域中的拒绝规则优先。缺省或仅有拒绝列表的策略不会授予应用工具；普通工具限制和展示仍使用上游实现。每次发出请求都解析当前凭据，每次执行都从实际 Agent 获取可信身份。携带凭据的 MCP HTTP 请求拒绝重定向。

MCP 桥接层仅接纳受支持的对象根输入模式，并在发送请求前使用原有 DSH 辅助函数验证参数。本地产生的 `ToolArgsError`/`INVALID_ARGS` 证明应用回调尚未执行，配额策略因此可以接纳修正后的请求。远程错误不能证明操作没有产生效果。本地插件通过 `@karaka-ai/agent/tools` 获取同一套工具定义、错误类和编写工具所需的类型。

应用配置及实现边界见[运行时说明](../../../../packages/karaka/agent/IMPLEMENTATION.md)。该决定增加 Karaka 行为，不取代任何有效的上游 Agent Note；DSH 已发布格式和原有插件契约保持不变。

## Alternatives considered

**替换 Session 及关联消费者。** 尚未发现必须修改引擎的要求。公开 setup、持久化和作用域注册 API 可以支持当前应用流程，无需重复 Session 类或复制反向依赖树。

**在 DSH JSONL 头中添加归属。** 这会修改严格的已发布格式及编解码器目录链。独立归属数据保留上游格式，代价是备份必须包含第二份持久数据。

**使用原有 MCP 配置提供应用工具。** 静态 HTTP 头和普通 Tools 注册无法提供可更新的凭据、可信执行元数据或私有应用目录。[共享扩展决策](2026-09-14-shared-mcp-extensions-for-karaka.zh.md)负责满足这些应用要求的程序化复用。

## Consequences

更新核心引擎时保留原有 Session、Agent、循环和 Tools 实现。Karaka 维护归属服务和应用适配器；共享 MCP 包提供链接决策中所述的通用扩展。归属数据和 Session 文件共同构成应用备份；单独的 Session JSONL 不能确立应用归属。发布跨越两个文件，而不是跨文件事务，因此写入顺序和恢复语义属于归属契约。

已构建的本地产物包含独立维护的 CLI、采用单一规范实例的上游构建包以及 Karaka 适配器。已安装依赖和必需 peer 依赖组成的图仅使用产物内部链接，无需重新解析注册表版本，即可保持每个上游工作区包的唯一运行时身份。应用浏览器路由要求明确配置 JWT 验证和来源；浏览器门面支持历史、提示、跟随和作用域交互。各预设必须明确选择允许应用工具。

当前配置暴露所选择的 Karaka 入口。插件选择决定暴露范围；额外工作区插件及其明确的用户和工作区访问集成不在本次发布范围内。独立服务端不是默认要求。工作线程身份、跨聊天工具、完整渲染浏览器 UI 和图片上传不在已执行场景内。子会话及引用适配器和更广泛的浏览器交互仍需进一步证据；单个应用流程不能证明完整产品一致性。其他原生平台和注册表发布属于后续工作。服务端草稿以选定的 DSH 基线和 Karaka 覆盖层替换旧 fork 文件树，并不声称已移植所有旧定制。旧 fork 的 CI 和部署配置尚未与此应用配置协调。

## Testing

启动守卫的执行顺序、嵌套 Loader 遍历、实际禁用表达式及入口就绪判断已根据源码审查。遵照用户不运行测试的要求，未执行启动测试或构建；运行时启动与关闭行为仍未验证。

唯一获授权的端到端场景在干净安装三个已暂存的 0.1.2-alpha.4 npm tarball 后，通过独立构建的 CLI 运行并通过：SDK 认证和聊天创建、实际 DSH 模型与工具执行、持久化后重启、通过浏览器门面读取历史并提示和跟随续聊，以及拒绝错误归属的 SDK 访问。服务端 tarball 包含 501 个捆绑包名称；其来源本地产物包含 515 个规范包实例，没有外部链接。原有 DeepSeek 提供器向确定性的本地 HTTP 模型夹具发送三次请求；独立构建的 SDK 承载一次经过认证的 MCP 工具调用。这不是实际 DeepSeek 服务的结果。浏览器门面在 Node 中使用明确的 Origin 夹具运行，没有渲染产品 UI。

证据记录于 `/tmp/karaka-application-flow-jZS1P4/evidence.json`，并由更新器保存在 `work/reuse-implementation/evidence.json`。依赖安装、原生扩展构建、运行时及浏览器打包和公共类型声明生成用于准备运行。[工作区规范一致性](../process/2026-09-14-karaka-workspace-conformance.zh.md)和[共享 MCP 扩展](2026-09-14-shared-mcp-extensions-for-karaka.zh.md)记录负责此产物场景之外的包集成与共享运行时验证。发布产物已暂存；注册表发布状态单独记录。更广泛的恢复、并发、子会话、工作线程和浏览器行为未由该场景验证。
