# Agent Note: 在保持上游运行时不变的前提下提供 Karaka 权限归属

Status: implemented

[English](2026-09-12-karaka-authority-over-upstream-runtime.md) | 中文

## Problem

Karaka 的持久聊天和应用工具需要应用、租户和用户隔离。把这些字段放入 DSH Session 头会要求修改严格的格式编解码器及其消费者。复制所有依赖包会扩大上游维护范围，却不能证明这些实现需要不同的行为。

## Decision

Karaka 应用配置复用 DSH 的 Session、Agent、循环、Tools、JSONL、查询和模型实现。独立身份服务使用原有 JSON 存储和 domain API，在 Session 文件之外保存持久权限归属。内核锁保证每个归属存储根目录只有一个写入者。创建过程先预留身份，在等待完成的 setup 中绑定实际尚未发布的 Session，并在归属数据和 Session 都持久化后确认成功。冷访问在引擎恢复前完成授权。子会话沿经过验证的持久父会话链解析归属。

Karaka HTTP 操作通过公开 API 调用原有引擎。应用配置使用上游 DSH 启动器及 Loader 就绪信号；整个插件树就绪前，应用路由拒绝请求。独立维护的 SDK 使用这些路由，不嵌入另一个 Session 实现。

现有 Karaka MCP 包拥有应用工具目录。其连接管理器和丰富工具结果转换逻辑衍生自两个 DSH 文件，精确版本记录在[来源清单](../../../../packages/karaka/mcp-application/UPSTREAM.json)中；两个文件都包含必要的接口改动。没有复制无需修改的依赖包。应用工具在符合条件的各个 Agent 作用域注册，不在全局注册；工具必须同时获得端点许可和预设的明确允许，继承作用域中的拒绝规则优先。缺省或仅有拒绝列表的策略不会授予应用工具；普通工具限制和展示仍使用上游实现。每次发出请求都解析当前凭据，每次执行都从实际 Agent 获取可信身份。携带凭据的 MCP HTTP 请求拒绝重定向。

应用配置及实现边界见[运行时说明](../../../../packages/karaka/agent/IMPLEMENTATION.md)。该决定增加 Karaka 行为，不取代任何有效的上游 Agent Note；DSH 已发布格式和原有插件契约保持不变。

## Alternatives considered

**替换 Session 及关联消费者。** 尚未发现必须修改引擎的要求。公开 setup、持久化和作用域注册 API 可以支持当前应用流程，无需重复 Session 类或复制反向依赖树。

**在 DSH JSONL 头中添加归属。** 这会修改严格的已发布格式及编解码器目录链。独立归属数据保留上游格式，代价是备份必须包含第二份持久数据。

**直接使用原有 MCP 提供应用工具。** 其公开 API 缺少发送请求时解析凭据、可信执行元数据以及未全局发布的应用目录。有限改写保留已有重连和结果转换行为，不修改上游 MCP。

## Consequences

更新上游引擎时可以保留原始文件。Karaka 维护归属服务、应用适配器及两个明确标记来源的 MCP 文件。归属数据和 Session 文件共同构成应用备份；单独的 Session JSONL 不能确立应用归属。发布跨越两个文件，而不是跨文件事务，因此写入顺序和恢复语义属于归属契约。

已构建的本地产物包含独立维护的 CLI、采用单一规范实例的上游构建包以及 Karaka 适配器。已安装依赖和必需 peer 依赖组成的图仅使用产物内部链接，无需重新解析注册表版本，即可保持每个上游工作区包的唯一运行时身份。应用浏览器路由要求明确配置 JWT 验证和来源；浏览器门面支持历史、提示、跟随和作用域交互。各预设必须明确选择允许应用工具。

普通 Host 共存仍是尚未决定的部署选择。工作线程身份、跨聊天工具、完整渲染浏览器 UI 和图片上传不在已执行场景内。子会话及引用适配器和更广泛的浏览器交互仍需进一步证据；单个应用流程不能证明完整产品一致性。其他原生平台和注册表发布属于后续工作。服务端草稿以选定的 DSH 基线和 Karaka 覆盖层替换旧 fork 文件树，并不声称已移植所有旧定制。旧 fork 的 CI 和部署配置尚未与此应用配置协调。

## Testing

唯一获授权的端到端场景在干净安装三个已暂存的 0.1.2-alpha.4 npm tarball 后，通过独立构建的 CLI 运行并通过：SDK 认证和聊天创建、实际 DSH 模型与工具执行、持久化后重启、通过浏览器门面读取历史并提示和跟随续聊，以及拒绝错误归属的 SDK 访问。服务端 tarball 包含 501 个捆绑包名称；其来源本地产物包含 515 个规范包实例，没有外部链接。原有 DeepSeek 提供器向确定性的本地 HTTP 模型夹具发送三次请求；独立构建的 SDK 承载一次经过认证的 MCP 工具调用。这不是实际 DeepSeek 服务的结果。浏览器门面在 Node 中使用明确的 Origin 夹具运行，没有渲染产品 UI。

证据记录于 `/tmp/karaka-application-flow-jZS1P4/evidence.json`，并由更新器保存在 `work/reuse-implementation/evidence.json`。依赖安装、原生扩展构建、运行时及浏览器打包和公共类型声明生成用于准备运行。没有执行其他测试或测试套件。发布产物已暂存；注册表发布状态单独记录。更广泛的恢复、并发、子会话、工作线程和浏览器行为未由该场景验证。
