# Agent Note: Karaka 上游集成的 CI 契约

Status: implemented

[English](2026-09-18-karaka-upstream-ci-contracts.md) | 中文

## Problem

上游重放同时引入运行时代码、测试和生成的参考文档。仓库字面量、职责转移及特定平台的夹具假设可能使验证失效，却不能证明运行时发生回归。新增适配器分支也需要自己的行为覆盖。

## Decision

Issue 策略请求的预期值使用[配置](../../../../.github/issue-management/config.json)指定的仓库，同时保留请求顺序、数量及策略断言。启动服务属于 Karaka 目录与关系图；可渲染的服务不能继续列为目录遍历豁免。生成的持久化显示名称可能重新排序，但类型结构与摘要保持不变。这种元数据漂移需要重新生成，而不是迁移或虚构历史转换。

[共享 MCP 扩展](../architecture/2026-09-14-shared-mcp-extensions-for-karaka.zh.md)保留扩展对象作为元数据回调的接收者。重叠调用保留独立执行委托：一次授权拒绝不能移除另一调用方的图像投影，也不能分派被拒绝的请求。原始工厂继续负责规范值、已准入图像存储及最终内容投影。

启动准入属于守卫，而非 HTTP 控制器。其覆盖使用实际 Loader 条目、有效禁用表达式和生命周期清理；路由夹具仅断言传输负责的配置与访问行为。Windows 驱动器相对路径基于所选驱动器的工作目录解析。依赖进程夹具使用现有 Windows CI 时间预算，不放宽生产基准阈值，也不移除断言。

这些验证契约补充 [Karaka 权限归属](../architecture/2026-09-12-karaka-authority-over-upstream-runtime.zh.md)及共享 MCP 决策；两者均未被取代。

## Alternatives considered

为了满足上游字面量而修改生产仓库路由，会指向错误仓库。宽泛的服务豁免、降低覆盖率阈值或手写猜测的模式，只会掩盖漂移，无法恢复验证依据。

## Testing

现有策略、文件系统及依赖解析夹具保留原有断言。MCP 扩展和启动覆盖验证上述职责。在此次修复中没有本地运行测试、E2E、构建、安装或生成器。只读 GitHub 工作流从已标识的源提交生成目录补丁，应用前已检查输出。更广泛的 GitHub CI 验证仍待完成，生成成功不等于测试套件通过。

## Consequences

配置、运行时行为及其验证继续分别承担各自职责。没有完整套件结果的工作进程退出仍是尚未解释的 CI 失败；仅凭缺失覆盖率不能修改工作进程行为或降低阈值。
